# Техническое задание на платформу «ВыборОк» (версия 1.0)

## 1. Общие цели и видение
Создать высокопроизводительную, масштабируемую и удобную платформу для создания и проведения опросов. Первоочередная цель — запуск MVP с базовым функционалом, но с архитектурой, позволяющей легко расширять возможности в будущем (соцсети, продвинутая защита, тёмная тема и т.д.).

---

## 2. Функциональные требования (детально)

### 2.1. Главная страница (`/`)
- Лендинг с описанием возможностей:
  - Создание опросов с разными типами вопросов (одиночный/множественный выбор, шкала, текстовый ответ).
  - Настройка доступа: публичный или только по ссылке.
  - Встраивание на внешние сайты (iframe).
  - Статистика с диаграммами в реальном времени.
  - Безопасность и защита (на будущее).
- Крупные кнопки «Войти» и «Зарегистрироваться».
- Адаптивный дизайн под мобильные и десктопы.

### 2.2. Аутентификация и профиль
- **Регистрация**: email + пароль (подтверждение email через ссылку). Восстановление пароля по email.
- **Вход**: по email и паролю. (В будущем — через Яндекс ID и другие соцсети.)
- **Профиль пользователя**: 
  - Аватар, username (уникальный, можно менять), имя, фамилия, описание, ссылки на соцсети.
  - Настройка приватности: **закрытый профиль** – полностью недоступен для неавторизованных; авторизованные видят только те поля, которые владелец явно пометил как общедоступные (по умолчанию ничего). При закрытом профиле страница `/username` для посторонних показывает только заглушку «Профиль скрыт» без опросов.
  - Открытый профиль – все видят шапку с аватаркой и списком публичных опросов.

### 2.3. Личный кабинет авторизованного пользователя
- Шапка: аватар, username, кнопка «Настройки» (переход к редактированию профиля).
- Лента созданных пользователем опросов (с пагинацией). Каждый опрос отображает:
  - Название, дату создания, статус (активен / завершён / черновик).
  - Количество участников, краткий процент проголосовавших.
  - Кнопки: «Редактировать» (если опрос ещё не начат или не завершён), «Завершить», «Удалить», «Посмотреть статистику», «Получить код встраивания».
- Плавающая кнопка «+» для создания нового опроса (открывает форму).

### 2.4. Создание и управление опросом
- **Форма создания** (пошаговый мастер):
  1. Заголовок (обяз.), описание (необяз.).
  2. Добавление вопросов:
     - Тип: одиночный выбор, множественный выбор, шкала (1–5 или 1–10), текстовый ответ.
     - Для выбора — варианты ответов (можно добавлять/удалять).
     - Возможность прикрепить мультимедиа (изображение, видео, аудио) к отдельному вопросу (ограничения по размеру: фото — до 10 МБ, видео — до 100 МБ, аудио — до 50 МБ; поддерживаемые форматы: JPEG, PNG, MP4, WebM, MP3, OGG). На первом этапе файлы хранятся локально на сервере, но структура каталогов проектируется с возможностью перехода на S3-совместимое хранилище.
  3. Настройки доступа:
     - Публичный (виден всем) / Только по ссылке (не индексируется, доступен только по прямой ссылке).
     - Разрешить голосование неавторизованным (да/нет).
     - Гео-ограничение: выбор стран (по IP-адресу). Например, только Россия.
  4. Настройка видимости результатов: сразу после голосования или после завершения опроса.
  5. Дата/время автоматического завершения (опционально).
  6. Кнопка «Создать» – опрос сохраняется со статусом «активен» (или «черновик», если добавить чекбокс «опубликовать позже» — пока опустим).
- **Редактирование**: разрешено до первого голоса или до даты старта. После появления голосов редактирование запрещено (можно только завершить/удалить).
- **Удаление**: опрос удаляется полностью со всеми данными (или архивируется — решим позже, пока просто удаление).

### 2.5. Страница опроса (прохождение)
- Уникальный URL, например `/poll/{id}`.
- Отображает название, описание, вопросы.
- Для авторизованных: голос привязывается к пользователю.
- Для неавторизованных: если разрешено, можно проголосовать без входа; результаты сохраняются без привязки к личности (только голос, без идентификатора). При этом выводится предупреждение, что анонимные голоса не защищены от накрутки.
- После отправки — проверка, не голосовал ли уже пользователь (для авторизованных — по user_id, для анонимных — никакой проверки, т.к. мы не идентифицируем). *Это временное решение; в будущем добавим CAPTCHA и ограничения по IP.*
- После голосования (или после завершения опроса) пользователь перенаправляется на страницу результатов.

### 2.6. Статистика и диаграммы
- Для каждого опроса доступна страница `/poll/{id}/stats`.
- Отображается:
  - Общее количество участников.
  - Для каждого вопроса с выбором — круговая диаграмма (можно переключить на столбчатую) с процентами и абсолютными числами.
  - Для вопросов-шкал — среднее значение, медиана, гистограмма распределения.
  - Для текстовых ответов — список всех ответов (с возможностью поиска).
  - Линейная диаграмма, показывающая динамику голосов по дням/часам (количество проголосовавших за период).
- Все диаграммы строятся на клиенте с использованием библиотеки (например, Chart.js) на основе данных, получаемых с бэкенда в формате JSON.
- **Экспорт**: кнопка «Скачать CSV» (сырые данные по каждому вопросу) и «Скачать PDF» (красивый отчёт со всеми диаграммами).
- Данные статистики обновляются в реальном времени при каждом новом голосе (благодаря асинхронному пересчёту и кэшированию).

### 2.7. Встраивание на внешние сайты
- В личном кабинете для каждого опроса генерируется iframe-код, например:
  ```html
  <iframe src="https://выборок.рф/embed/{poll_id}" width="100%" height="600" frameborder="0"></iframe>
  ```
- Параметры настройки (пока минимальные): можно указать ширину и высоту, скрыть заголовок.
- **На будущее**: расширенный JavaScript-виджет с кастомизацией цветов и событий (пока не реализуем, но API спроектировать с заделом).

### 2.8. Защита от накрутки (отложено на второй этап)
- В MVP мы не внедряем CAPTCHA и IP-лимиты. Вместо этого:
  - При создании опроса выводим предупреждение о рисках при анонимном голосовании.
  - В будущем планируем: CAPTCHA при голосовании для неавторизованных, ограничение по IP за период, возможно использование fingerprint.

## 3. Нефункциональные требования и архитектура

### 3.1. Технологический стек
- **Фронтенд**: Angular 16+ (TypeScript, RxJS, Angular Material или кастомный дизайн на основе CSS-фреймворка, например Tailwind). Сборка через Angular CLI.
- **Бэкенд**: Go 1.21+ с фреймворком `github.com/unistack-org/micro` (REST API, gRPC для внутреннего общения). Микросервисы:
  - **Auth** (аутентификация, профили)
  - **Poll** (управление опросами)
  - **Vote** (приём голосов)
  - **Stats** (агрегация статистики)
  - **Media** (загрузка и хранение файлов)
  - **Embed** (генерация iframe и обслуживание виджетов)
- **Базы данных**:
  - **PostgreSQL** – основная реляционная БД для пользователей, опросов, вопросов, вариантов, голосов (связка с пользователями).
  - **Redis** – кэш для:
    - сессий и JWT-токенов,
    - кэшированных страниц и результатов опросов (уменьшение нагрузки на БД),
    - агрегированных статистических данных (инвалидация при каждом голосе).
  - **Аналитическая БД** (для будущего): сейчас статистика вычисляется на основе голосов в PostgreSQL, но для линейных графиков и больших объёмов можно использовать ClickHouse или TimescaleDB. Пока ограничимся PostgreSQL + Materialized Views или триггерами, но спроектируем схему так, чтобы легко мигрировать.
- **Очереди сообщений**: NATS (легковесный, хорошо интегрируется с Go) – для асинхронных задач:
  - отправка писем (подтверждение email, восстановление пароля),
  - обновление статистики после голосования (чтобы не тормозить основной запрос),
  - генерация превью для медиа.
- **Хранилище файлов**: локальная файловая система (в продакшене — смонтированный том). В перспективе — MinIO или Amazon S3.
- **Контейнеризация и оркестрация**: Docker-образы для каждого микросервиса. Для оркестрации рекомендую **Kubernetes** (даже для небольшой нагрузки), потому что:
  - он обеспечивает автоматическое восстановление при сбоях,
  - упрощает масштабирование (можно увеличить реплики для Vote-сервиса при пике),
  - поддерживает rolling updates без простоя,
  - имеет встроенные механизмы health-проверок и конфигурации (ConfigMap, Secrets).
  - Для разработки можно использовать Docker Compose.
- **Мониторинг и логирование**:
  - **Prometheus** + **Grafana** для сбора метрик (количество запросов, ошибки, задержки, использование ресурсов).
  - **ELK Stack** (Elasticsearch, Logstash, Kibana) рекомендую для централизованного сбора и анализа логов. Это поможет быстро находить ошибки и отслеживать поведение системы. Альтернатива — Loki (легче), но ELK даёт больше возможностей.
- **CI/CD**: GitLab CI или GitHub Actions для автоматической сборки, тестирования и деплоя в Kubernetes.

### 3.2. Требования к производительности и масштабируемости
- **Начальная цель**: 100 одновременных пользователей (голосующих) без деградации.
- **Архитектура** позволяет горизонтально масштабировать любые сервисы. Ожидаем, что при росте до 1000+ пользователей достаточно увеличить число реплик Vote, Stats и Poll, а также увеличить размер Redis-кластера.
- Кэширование: все GET-запросы к опросам (особенно публичным) кэшируются в Redis на 1 минуту (или до инвалидации).
- Использование очередей для асинхронных задач снижает нагрузку на основной API.

### 3.3. Отказоустойчивость
- Каждый микросервис должен иметь health-эндпоинты (`/health`), которые проверяют подключение к БД, Redis, очереди.
- Kubernetes будет автоматически перезапускать упавшие поды.
- Репликация PostgreSQL (master-slave) с автоматическим переключением (например, с использованием Patroni или оператора CloudNativePG).
- Redis – в режиме Sentinel для высокой доступности.
- Все сервисы проектируются stateless, чтобы их можно было легко масштабировать.

### 3.4. Безопасность
- Все пароли хешируются bcrypt.
- JWT-токены с коротким временем жизни (access + refresh токены).
- Все эндпоинты, кроме публичных (главная, страница опроса, публичные профили), требуют аутентификации.
- CORS настроен для разрешённых доменов (для встраивания).
- Валидация всех входных данных (использование структур с тегами `validate` в Go).
- Защита от CSRF (используем SameSite Cookie для refresh-токена).
- HTTPS обязателен (сертификаты Let's Encrypt).

### 3.5. Локализация и дизайн
- Поддержка двух языков: русский и английский (перевод интерфейса через Angular i18n).
- Цветовая схема: светлая, на основе белого/светло-бежевого («старая бумага») с акцентным цветом (предлагаю тёплый оранжевый или тёмно-синий для контраста). Брендинг: логотип пока отсутствует, но будет использоваться значок «ВО👍» в заголовке.
- Адаптивность: три брейкпоинта (десктоп, планшет, мобильный телефон). На мобильных упрощённая навигация (гамбургер-меню).

## 4. Модель данных (базовые сущности)

### PostgreSQL (основная БД)

```sql
-- пользователи
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    username VARCHAR(50) UNIQUE NOT NULL,
    first_name VARCHAR(100),
    last_name VARCHAR(100),
    bio TEXT,
    links JSONB, -- массив ссылок
    avatar_url VARCHAR(255),
    is_private BOOLEAN DEFAULT FALSE,
    public_fields JSONB, -- список полей, видимых при закрытом профиле
    email_verified BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);

-- опросы
CREATE TABLE polls (
    id UUID PRIMARY KEY,
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(255) NOT NULL,
    description TEXT,
    status VARCHAR(20) DEFAULT 'active', -- active, closed, draft
    access_type VARCHAR(20) DEFAULT 'public', -- public, private
    allow_unauth BOOLEAN DEFAULT TRUE,
    geo_countries TEXT[] NULL, -- список стран (ISO-коды)
    show_results VARCHAR(20) DEFAULT 'immediate', -- immediate, after_close
    close_at TIMESTAMP NULL,
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);

-- вопросы
CREATE TABLE questions (
    id UUID PRIMARY KEY,
    poll_id UUID REFERENCES polls(id) ON DELETE CASCADE,
    question_text TEXT NOT NULL,
    question_type VARCHAR(20) NOT NULL, -- single, multiple, scale, text
    order_index INT NOT NULL,
    scale_min INT DEFAULT 1,
    scale_max INT DEFAULT 5,
    media_url VARCHAR(255) NULL,
    created_at TIMESTAMP
);

-- варианты ответов (для single/multiple)
CREATE TABLE options (
    id UUID PRIMARY KEY,
    question_id UUID REFERENCES questions(id) ON DELETE CASCADE,
    option_text VARCHAR(255) NOT NULL,
    order_index INT NOT NULL
);

-- голоса
CREATE TABLE votes (
    id UUID PRIMARY KEY,
    poll_id UUID REFERENCES polls(id) ON DELETE CASCADE,
    question_id UUID REFERENCES questions(id) ON DELETE CASCADE,
    user_id UUID NULL REFERENCES users(id) ON DELETE SET NULL,
    option_id UUID NULL REFERENCES options(id) ON DELETE SET NULL,
    text_value TEXT NULL, -- для текстовых ответов
    scale_value INT NULL, -- для шкалы
    ip_address INET NULL,
    session_id UUID NULL, -- для анонимных
    created_at TIMESTAMP
);

-- (опционально) таблица для статистики, агрегированной по часам/дням
CREATE TABLE poll_stats_daily (
    poll_id UUID REFERENCES polls(id),
    date DATE,
    total_votes INT,
    PRIMARY KEY (poll_id, date)
);
```

**Индексы**: на `user_id` в polls, на `poll_id` в вопросах/голосах, на `created_at` для сортировки.

### Redis (кэш)
- Ключи вида `poll:{id}:data` – полная структура опроса (с вопросами и вариантами) для быстрой отдачи.
- `poll:{id}:stats` – агрегированная статистика для страницы результатов.
- `user:{id}:profile` – кэш профиля для публичных страниц.
- Сессии пользователей (JWT refresh) хранятся в Redis с TTL.

## 5. Интерфейсы микросервисов (основные эндпоинты)

Все сервисы используют gRPC для внутреннего общения, REST для внешних клиентов (через API Gateway на основе `micro`).

### Сервис Auth
- `POST /auth/register` – регистрация
- `POST /auth/login` – вход (возвращает access/refresh токены)
- `POST /auth/refresh` – обновление токена
- `POST /auth/logout`
- `POST /auth/forgot-password` – запрос на сброс
- `POST /auth/reset-password` – сброс по токену
- `GET /auth/verify-email/{token}` – подтверждение email
- `GET /user/{username}` – публичный профиль (с учётом приватности)
- `PUT /user/profile` – обновление профиля (авторизованный)
- `POST /user/avatar` – загрузка аватарки

### Сервис Poll
- `POST /polls` – создать опрос
- `GET /polls` – список опросов текущего пользователя (с пагинацией)
- `GET /polls/{id}` – получить опрос (с вопросами)
- `PUT /polls/{id}` – обновить (если разрешено)
- `DELETE /polls/{id}` – удалить
- `POST /polls/{id}/close` – завершить досрочно
- `GET /polls/user/{username}` – публичные опросы пользователя (для открытых профилей)

### Сервис Vote
- `POST /polls/{id}/vote` – проголосовать (передаётся массив ответов: question_id + option_id/text/scale)
- `GET /polls/{id}/has-voted` – проверка, голосовал ли текущий пользователь (для авторизованных)

### Сервис Stats
- `GET /polls/{id}/stats` – получить статистику в формате JSON (данные для диаграмм)
- `GET /polls/{id}/stats/export/csv` – выгрузка CSV
- `GET /polls/{id}/stats/export/pdf` – выгрузка PDF (генерируется на сервере или клиенте?)

### Сервис Media
- `POST /media/upload` – загрузка файла (возвращает URL)
- `GET /media/{filepath}` – отдача файла (для локального хранилища)

### Сервис Embed
- `GET /embed/{poll_id}` – HTML-страница для встраивания (без шапки/футера, только опрос)
- `GET /embed/{poll_id}/script.js` – (на будущее) JavaScript-виджет

## 6. Сценарии интеграции и потоков данных

### При создании опроса:
1. Клиент отправляет POST /polls с данными (включая файлы мультимедиа – сначала загружаются через Media, затем ссылки передаются в Poll).
2. Poll-сервис сохраняет данные в PostgreSQL, отправляет событие в очередь (например, «poll_created») для индексации (пока не нужно).
3. Возвращает ID опроса и ссылку.

### При голосовании:
1. Клиент отправляет POST /polls/{id}/vote.
2. Vote-сервис проверяет авторизацию и доступ (гео, статус опроса, разрешены ли анонимы).
3. Проверяет, не голосовал ли уже пользователь (для авторизованных).
4. Сохраняет голос в PostgreSQL.
5. Отправляет событие в очередь `vote_recorded` с данными голоса.
6. Stats-сервис, получив событие, асинхронно пересчитывает статистику, обновляет Redis-кэш и (опционально) агрегирует данные в таблицу `poll_stats_daily`.
7. Клиенту возвращается успех.

### При запросе статистики:
1. Клиент запрашивает GET /polls/{id}/stats.
2. Stats-сервис сначала проверяет Redis – если есть актуальный кэш, отдаёт его.
3. Иначе делает запросы к PostgreSQL для расчёта (материализованные представления или сложные запросы) и сохраняет результат в Redis с TTL (например, 5 минут).
4. Отдаёт клиенту JSON.

### При загрузке страницы опроса (публичной):
- Для неавторизованных: Poll-сервис отдаёт данные опроса, кэшируя их в Redis на короткое время (1 минута).
- Для авторизованных: возвращает с пометкой, голосовал ли пользователь.

## 7. Дизайн и пользовательский интерфейс (подробнее)

- **Главная**: Hero-блок с логотипом «ВО👍» и слоганом, затем блоки с иконками фич.
- **Форма создания опроса**: разбита на шаги (как в Google Forms). Слева – навигация по шагам, справа – редактируемая область.
- **Страница опроса**: центрированная карточка, вопросы с радиокнопками/чекбоксами/полем ввода. Поддержка мультимедиа в вопросах.
- **Страница статистики**: вкладки «Обзор», «По вопросам», «Динамика». Графики интерактивные (при наведении показываются значения).
- **Профиль пользователя**: лента опросов в виде карточек (как в соцсетях). Плавающая кнопка «+».
- **Адаптив**: на мобильных шапка сворачивается, карточки опросов становятся на всю ширину, кнопка «+» уменьшается.

## 9. Рекомендации по инфраструктуре

### Kubernetes
- Используйте **Minikube** для локальной разработки, в продакшене – управляемый кластер (например, в Yandex Cloud, AWS EKS или Google GKE). Это даст автоматическое масштабирование, самовосстановление и упростит управление конфигурациями.
- Для управления базами данных в K8s используйте операторы (например, CloudNativePG для PostgreSQL, Redis Operator для Redis).

### ELK Stack
- Вместо полноценного ELK можно начать с **Loki** (легче, интегрируется с Grafana) для сбора логов, но ELK даст более мощный поиск и визуализацию. Рекомендую развернуть EFK (Elasticsearch, Fluentd, Kibana) – Fluentd собирает логи с подов и отправляет в Elasticsearch.

### Очереди
- **NATS** – отличный выбор для Go-микросервисов, поддерживает at-least-once, легко масштабируется. Можно использовать JetStream для персистентности.

### Мониторинг
- Prometheus собирает метрики с каждого сервиса (через экспортеры). Grafana предоставляет дашборды. Обязательно настроить алерты (например, при высокой задержке или ошибках 5xx).

## 10. Дополнительные замечания

- **Подтверждение email**: при регистрации отправляется письмо со ссылкой; ссылка действительна 24 часа.
